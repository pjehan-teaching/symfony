MCP - Model Context Protocol

Le problème

Un assistant IA (Claude, ChatGPT, Copilot...) ne connaît ni vos données ni vos applications.

  • Chaque assistant a sa propre façon de brancher des outils
  • Chaque application doit écrire une intégration par assistant
  • Résultat : N assistants × M applications d'intégrations à maintenir

MCP standardise cette connexion : une application expose un serveur MCP, tous les clients compatibles peuvent l'utiliser.

Introduction à MCP

Qu'est-ce que MCP ?

  • Protocole ouvert créé par Anthropic (fin 2024), aujourd'hui adopté par tout l'écosystème
  • Messages au format JSON-RPC 2.0
  • Inspiré du Language Server Protocol (LSP) : un protocole commun entre éditeurs et langages
  • Versionné par date : la révision actuelle est 2026-07-28

Analogie : MCP est le « port USB-C » des applications pour l'IA.

Spécification

Architecture

  • Host : l'application d'IA que l'utilisateur manipule (Claude Desktop, Claude Code, VS Code, Cursor...)
  • Client : le connecteur, intégré au host, qui parle à un serveur
  • Serveur : le programme qui expose des capacités (c'est ce que nous allons écrire)

Un host peut ouvrir plusieurs clients, donc se connecter à plusieurs serveurs en même temps.

Server features

Les transports

Deux façons standard de transporter les messages :

  • stdio : le client lance le serveur comme sous-processus local et échange via stdin / stdout. Idéal en développement et pour les outils locaux.
  • Streamable HTTP : chaque message est un POST HTTP vers un endpoint unique (ex. /mcp). Pour les serveurs distants.

⚠️ L'ancien transport HTTP+SSE est déprécié.

Transports

Ce qui a changé récemment

La révision 2026-07-28 rend le protocole sans état :

  • Plus de handshake initialize : chaque requête porte sa version et les capacités du client dans _meta
  • Plus de session (Mcp-Session-Id supprimé) : un serveur MCP se comporte comme une API HTTP classique
  • Nouvelle méthode server/discover pour connaître version, capacités et identité d'un serveur
  • Tasks (tâches longues) déplacées dans une extension
  • Roots, Sampling et Logging sont dépréciés
Key changes

Ce qui a changé récemment

  • Les requêtes serveur → client (elicitation...) passent par un modèle multi-aller-retour : le serveur répond « j'ai besoin d'une information » et le client rejoue la requête avec la réponse
  • Les listes (tools/list...) indiquent une durée de cache (ttlMs, cacheScope)
  • Authentification : Client ID Metadata Documents préférés à l'enregistrement dynamique de clients (DCR, déprécié)

Les tutoriels antérieurs à mi-2026 décrivent souvent initialize et les sessions : ils sont en partie obsolètes.

Un échange concret : appeler un tool

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "current-time",
    "arguments": { "format": "H:i" },
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}

La réponse contient un tableau content (texte, image...) lu par le modèle :

{ "jsonrpc": "2.0", "id": 1,
  "result": { "resultType": "complete", "content": [{ "type": "text", "text": "14:32" }] } }
Tools

Le cycle de vie d'un tool

  1. Le client appelle tools/list : le serveur renvoie nom, description et schéma JSON des paramètres
  2. Le host donne ces descriptions au modèle
  3. Le modèle décide d'appeler un tool et produit les arguments
  4. Le client envoie tools/call (avec la validation de l'utilisateur)
  5. Le résultat revient dans le contexte du modèle

La qualité des descriptions détermine la qualité de l'usage du tool par le modèle.

Sécurité : les principes de la spécification

  • Un tool = exécution de code arbitraire : l'utilisateur doit consentir à chaque usage sensible
  • Les descriptions de tools d'un serveur tiers sont non fiables (risque d'injection de prompt)
  • Pour un serveur distant : authentification OAuth 2.1 ; le serveur MCP est un resource server : il ne gère pas l'authentification, il vérifie seulement les tokens délivrés par un serveur d'autorisation
  • Principe du moindre privilège : n'exposez que ce qui est nécessaire, préférez la lecture seule

Le MCP Bundle de Symfony

Présentation

Le MCP Bundle intègre le SDK PHP officiel (mcp/sdk) dans Symfony :

  • Capacités déclarées par des attributs PHP sur des services
  • Transports stdio et HTTP prêts à l'emploi
  • Accès à tout le conteneur : Doctrine, Security, Mailer...
  • Commande debug:mcp et panneau dans le Profiler

Une capacité = une classe PHP avec un attribut.

MCP Bundle

Installation

composer require symfony/mcp-bundle

Pour exposer le serveur en HTTP, ajoutez la route :

# config/routes.yaml
mcp:
    resource: .
    type: mcp
MCP Bundle

Configuration

# config/packages/mcp.yaml
mcp:
    servers:
        default:
            name: 'my-app'
            transports:
                stdio: true   # symfony console mcp:server default
                http: true    # route /mcp/default
            registry: ['App\Mcp\']
  • registry est obligatoire : le serveur n'expose que ce qu'il liste (namespace, classe ou *)
  • On peut déclarer plusieurs serveurs nommés, avec des capacités différentes
MCP Bundle

Mon premier tool

namespace App\Mcp;

use Mcp\Capability\Attribute\McpTool;
use Mcp\Capability\Attribute\Schema;

final class CurrentTimeTool
{
    #[McpTool(name: 'current-time', description: 'Donne l\'heure actuelle (UTC)')]
    public function __invoke(
        #[Schema(description: 'Format de date PHP')]
        string $format = 'Y-m-d H:i:s',
    ): string {
        return (new \DateTimeImmutable('now', new \DateTimeZone('UTC')))->format($format);
    }
}

Le schéma JSON des paramètres est généré à partir des types PHP.

Un tool métier avec injection

La classe est un service : on injecte ce que l'on veut.

final class SearchProductsTool
{
    public function __construct(private ProductRepository $products) {}

    #[McpTool(
        name: 'search-products',
        description: 'Recherche des produits du catalogue par nom',
    )]
    public function __invoke(
        #[Schema(description: 'Texte à chercher dans le nom', minLength: 2)]
        string $query,
        #[Schema(description: 'Nombre maximum de résultats', minimum: 1, maximum: 20)]
        int $limit = 5,
    ): array {
        return array_map(
            fn (Product $p) => ['id' => $p->getId(), 'name' => $p->getName(), 'price' => $p->getPrice()],
            $this->products->search($query, $limit),
        );
    }
}
MCP Bundle

Bonnes pratiques pour un tool

  • Un nom explicite et une description qui dit quand l'utiliser
  • Décrire chaque paramètre avec #[Schema]
  • Retourner des données compactes (le résultat consomme le contexte du modèle)
  • Valider les entrées : les arguments viennent d'un modèle, jamais de confiance
  • Séparer lecture et écriture ; confirmer les actions destructrices
  • Lever une exception avec un message clair plutôt que renvoyer une erreur obscure

Resources et resource templates

Une resource expose des données identifiées par une URI :

#[McpResource(uri: 'app://about', name: 'about', mimeType: 'text/plain')]
public function about(): string
{
    return 'Boutique de démonstration';
}

#[McpResourceTemplate(uriTemplate: 'product://{id}', name: 'product')]
public function product(int $id): array
{
    $p = $this->products->find($id);
    return ['uri' => "product://$id", 'mimeType' => 'text/plain', 'text' => $p?->getName() ?? ''];
}

Le template ({id}) couvre une famille de ressources.

Server features

Prompts

use Mcp\Capability\Attribute\McpPrompt;

final class ReviewPrompts
{
    #[McpPrompt(name: 'review-product')]
    public function __invoke(string $productName): array
    {
        return [
            ['role' => 'user', 'content' => "Rédige une fiche produit pour : $productName"],
        ];
    }
}

Les prompts apparaissent chez l'utilisateur comme des commandes (ex. /review-product dans certains clients).

Tester avec le MCP Inspector

Outil officiel pour appeler son serveur sans passer par une IA :

npx @modelcontextprotocol/inspector php bin/console mcp:server default

L'interface web s'ouvre sur http://localhost:6274 : liste des tools, formulaire d'appel, historique des messages JSON-RPC.

Pour tester en HTTP depuis le navigateur, autorisez l'origine de l'Inspector :

mcp:
    servers:
        default:
            http:
                allowed_origins: ['http://localhost:6274']
MCP Inspector

Connecter un vrai client

Exemple avec Claude Code :

# Serveur local en stdio
claude mcp add my-app -- php /chemin/vers/projet/bin/console mcp:server default

# Serveur HTTP (symfony serve)
claude mcp add --transport http my-app https://127.0.0.1:8000/mcp/default

La plupart des clients (Claude Desktop, VS Code, Cursor...) se configurent avec un fichier JSON équivalent :

{ "mcpServers": { "my-app": {
    "command": "php", "args": ["/chemin/vers/projet/bin/console", "mcp:server", "default"] } } }

Sécuriser son serveur Symfony

  • DNS rebinding : seuls localhost et la même origine sont acceptés ; en production, listez vos domaines dans allowed_hosts
  • Authentification : protégez la route avec le composant Security
# config/packages/security.yaml
security:
    access_control:
        - { path: ^/mcp, roles: ROLE_USER }
  • Plusieurs serveurs = plusieurs niveaux d'accès (/mcp/editors, /mcp/admin)
  • Ne jamais partager le même store de sessions entre deux serveurs

Exercice - Un serveur MCP pour mon application

Ajoutez un serveur MCP à votre application Symfony existante (ou à un nouveau projet) et utilisez-le depuis un assistant IA.

  1. Installez symfony/mcp-bundle, ajoutez la route et la configuration (stdio + HTTP)
  2. Créez le tool current-time et vérifiez-le avec debug:mcp
  3. Créez un tool lecture seule qui interroge vos entités (recherche, détail...) avec des paramètres décrits via #[Schema]
  4. Ajoutez une resource ou un prompt
  5. Testez avec le MCP Inspector, puis connectez votre serveur à Claude Code ou à votre éditeur
  6. Bonus : protégez la route HTTP avec access_control
